# WAL 分段与安全回收

核对日期：2026-11-02。本次在 Actor 路径引入分段与回收；同步写库基线 `cmd/server` 仍使用原来的单文件 WAL，不能把下文回收能力套到同步基线上。

## 参考了 etcd 的哪些实现

实际读取 etcd **v3.5.17**，标签解析到固定提交 `507c0de87bd5034e3de4ab76ebf96b54dae0cd52`。以下是源码依据，不是声称本 Demo 获得了 etcd 的可靠性或 Raft 能力。

| 官方源码 | 实际做法 | 借鉴到 Demo 的原则 |
| --- | --- | --- |
| [server/wal/wal.go：cut、ReleaseLockTo、SaveSnapshot](https://github.com/etcd-io/etcd/blob/507c0de87bd5034e3de4ab76ebf96b54dae0cd52/server/wal/wal.go) | `cut` 同步旧段、新段的头与状态，再重命名并同步目录；`ReleaseLockTo` 释放旧锁但保留边界段；`SaveSnapshot` 写入并同步快照标记 | 切段与恢复边界必须可持久识别；不能只调用 rename/remove 就认为安全 |
| [server/etcdserver/storage.go：SaveSnap、Release](https://github.com/etcd-io/etcd/blob/507c0de87bd5034e3de4ab76ebf96b54dae0cd52/server/etcdserver/storage.go) | 先保存快照文件，再保存 WAL 快照标记；允许留下孤立快照，避免出现“日志引用不存在的快照”；`Release` 在快照位置释放旧 WAL 资源 | 先建立可靠恢复依据，再允许旧日志失去保护 |
| [server/etcdserver/server.go：snapshot、purgeFile](https://github.com/etcd-io/etcd/blob/507c0de87bd5034e3de4ab76ebf96b54dae0cd52/server/etcdserver/server.go) | `snapshot` 先提交 backend 一致性位置，再创建并保存 Raft 快照、释放旧资源；内存 Raft 日志压缩还考虑慢 follower 和正在发送的快照；`purgeFile` 启动保留数量清理 | 判断回收安全性需要理解所有恢复使用者，不能只看“文件旧了” |
| [client/pkg/fileutil/purge.go：purgeFile](https://github.com/etcd-io/etcd/blob/507c0de87bd5034e3de4ab76ebf96b54dae0cd52/client/pkg/fileutil/purge.go) | 按文件名排序、保留配置数量；WAL 清理先尝试文件锁，无法取得则停止本轮，实际删除独立于快照保存 | 数量策略不能越过安全边界；正在使用的文件不能删除 |

etcd 的安全依据包括 Raft 状态、快照位置和文件锁。本项目的依据是 **MongoDB 已确认的玩家快照及本地日志清单**，没有 follower、Raft commit index 或选主。这里没有复制 etcd 的数据格式或直接调用其清理函数，也不把 MVCC 历史版本 compaction、数据库 defrag 与 WAL 文件回收混为一谈。

## 什么时候能删除

每个 Actor 分片有独立的分段日志。一个段必须同时满足：

1. 已停止接受新资产事件，且不是当前活动段。
2. 段内没有 pending 事件，完成标记已可靠记录。
3. 每个事件所属玩家的 MongoDB 已确认快照序号，不小于该事件序号。
4. 能把新的恢复清单和已回收历史的证明可靠保存下来。

采用保守的**连续前缀回收**：从最旧段开始检查，遇到尚不安全的段就停止，不跨过它去删更后的段。一个玩家的成功落库不能授权删除其他玩家仍未落库的事件，也不能简单取所有玩家序号的最小值作为全局进度，因为各玩家的序号不连续，空闲玩家不一定有新事件。

```text
段1：A101、B102、A103    → 全部被各自的可靠快照覆盖，具备回收条件
段2：C104、A105         → C104未落库，保留，并停止前缀回收
段3：B106              → 即使B已落库，也暂不越过段2回收
段4：当前追加段         → 始终保留
```

“封存”在这里指不再接受新事件；旧段仍可能追加完成标记。全局事件序号通过每段的基序号映射，不能因为删除旧段就从1重新编号。

## 回收的持久化顺序

```text
MongoDB 保存：玩家资产 + 回执 + seq，可靠确认
                    ↓
WAL 记录完成标记并同步
                    ↓
检查可回收的封存段连续前缀
                    ↓
新清单记录：保留哪些段 + 已回收的玩家序号证明
                    ↓
临时清单写完并 fsync → 原子替换 → fsync 目录
                    ↓
删除不再被清单引用的旧段 → fsync 目录
```

删除的是整段，不在大文件中逐条挖洞。当前活动段保留，因此正常运行后文件体积不会归零。默认分段阈值为64 MiB，通过 `ACTOR_WAL_SEGMENT_BYTES` 调整；阈值是软边界，单批写入和完成标记可以使段超过阈值，下次追加新事件前再切段。

MongoDB 保存失败时不推进对应检查点、不因定时器到期就删除日志。未落库事件预算仍用于背压；它不是日志文件大小的硬上限。数据库故障、长期不能推进的前缀、磁盘空间和回收失败仍需要监控。

## 崩溃后如何选择恢复路径

| 崩溃位置 | 重启后依据 |
| --- | --- |
| MongoDB 尚未确认 | 保留事件，按原结果和幂等回执恢复 |
| MongoDB 已确认，完成标记未写完 | 用快照序号识别已覆盖事件，避免再次应用 |
| 新清单尚未可靠发布 | 旧清单仍保护旧段，不提前删除 |
| 新清单已发布，旧段尚未删除 | 新清单决定恢复集合，旧段只是待清理残留 |
| 只删除了部分旧段 | 根据已发布清单继续幂等清理，不依赖残留文件推测新历史 |
| 清单引用的段丢失或内容损坏 | 拒绝静默启动，不能把它当作正常回收 |

回收清单带校验，并通过稳定目录锁保护；锁不依附即将删除的活动数据文件。启动只清理按命名规则识别、且不再被有效清单引用的文件，不把目录里任意未知文件当作垃圾。清单缺失但目录已有分段历史时，不自动创建空历史。

## 删除原事件后，如何发现 MongoDB 快照丢失

如果只删除日志而不保存额外证明，未来误删玩家快照时可能无法区分“从未存在的玩家”和“历史资产被丢了”。因此清单保留每个受回收影响玩家的退休水位，例如 `A:103、B:102`。

恢复时要求 MongoDB 中 A、B 的快照分别覆盖这些水位；缺失或落后就拒绝启动。保留段内已完成事件也继续参与覆盖检查。这份证明只保留每玩家的最大必要序号，大小随玩家数量增长，不随每条历史事件增长。它**不是玩家资产备份**，不能替代 MongoDB 快照里的资产和幂等回执。

这也意味着不能随意恢复一个更旧的 MongoDB 备份并接上已经回收历史的当前 WAL。应将数据库、日志身份、回收清单及必要日志段作为一致的恢复集合规划；不满足覆盖检查时应恢复匹配备份，而不是删除清单来强制启动。

## 兼容旧日志与运维

Actor 仍使用原 `WAL_DIRECTORY` 和分片路径。首次启用分段时，原单文件作为初始段纳入清单，不丢弃未完成事件、不重置序号。后续轮转段与清单位于该分片日志的 `.segments` 侧目录。不要手工删除原文件、清单或侧目录；原文件作为初始段满足回收条件后，也可以由协议正常回收。

分段启用前，本地 `layout.json` 会保留随机日志身份并原子升级到schema 3，旧版schema 2日志可自动接纳。旧程序只接受schema 2，会拒绝新布局，避免忽略侧目录而丢失新事件。**不支持直接降级启动**，不能手工把schema改回去。需要降级或跨环境迁移时，应先设计显式迁移及备份流程。整个 Actor 目录及 MongoDB 的日志身份绑定仍需保留；本地锁和身份绑定不等于分布式 fencing。

观察 `/debug/stats` 和 `/metrics` 中的日志段数、保留字节和已回收数量，并结合 pending、检查点错误和磁盘空间判断。pending归零不代表活动段为空；累计回收计数也不代表操作系统/云盘的实际写放大。

本次实现及测试结果应以当前代码和 [验证记录](validation.md) 为准。故障注入测试覆盖的软件边界不能直接提升为“真实断电、坏盘或跨机接管已验证”。日志回收也不会清理玩家幂等回执，MongoDB单文档与回执生命周期仍是独立问题。


## 当前实现的性能边界

回收检查目前在分片检查点确认流程中同步扫描候选段，并持有日志互斥锁。扫描、清单同步和删除期间，同分片新写入可能等待；不宣称回收对延迟没有影响。64MiB候选段、磁盘抖动及多段积压时应测p99，并继续考虑安全的增量索引和后台回收拆分。

清单发布失败或删除失败后，相关分片停止写入并要求重启恢复。初始清单发布被中断、只残留临时清单且没有编号段时，可以验证并重新接纳旧单文件；目录已有编号历史却缺失清单时拒绝猜测恢复。

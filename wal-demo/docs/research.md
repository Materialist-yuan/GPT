# 从开源游戏后端学习：内存状态、持久日志与快照

核对日期：2026-11-02。本页依据实际读取的官方文档和源码编写，引用固定提交，避免分支更新后无法复现。没有采用无法核实的“某公司百万在线”数字，也没有把单机 Demo 的测试结果外推到生产集群。

## 结论：按故障边界选择架构

游戏后端不需要把每一次位置变化、金币变动和充值到账都用同一套持久化方式处理。

- 高频且可回退的状态，可以主要在内存中处理，再周期性保存。
- 不能因为进程重启就丢失的资产操作，需要在成功响应前建立明确的持久化保证；可以是数据库事务，也可以是已落盘的日志。
- 充值、跨玩家交易涉及外部系统或多个所有者，要另外设计事务、幂等和对账协议。
- 本机日志只能覆盖承诺范围内的磁盘持久性；丢盘、丢节点后仍要求保留已确认操作，需要复制日志、可靠存储或远端数据库确认。

本仓库保留同步 MongoDB 基线，便于与 actor 路径比较。actor 设计把资产逻辑放进内存中的单写者队列，先持久化确定的结果事件，再更新可见状态并响应，MongoDB 在后台保存带进度的快照。它是一个可检查故障语义的学习实现，不是 Orleans、Nakama 或 Redis 的移植。

## 1. Orleans：单写者降低并发推理成本，但不自动持久化

来源：Microsoft 维护的 `dotnet/docs`，固定提交 `bcbe167f3f4c10a1ad845283784184ec69af4616`。

- [Request scheduling](https://github.com/dotnet/docs/blob/bcbe167f3f4c10a1ad845283784184ec69af4616/docs/orleans/grains/request-scheduling.md)：说明 grain activation 使用单线程执行模型，默认情况下当前请求完成后才开始下一个请求。原文短句为 “a *single-threaded* execution model”。文档还区分 reentrant 的交错执行与真正的并行执行。
- [Grain persistence：Read state / Write state / Storage provider semantics](https://github.com/dotnet/docs/blob/bcbe167f3f4c10a1ad845283784184ec69af4616/docs/orleans/grains/grain-persistence/index.md)：激活时加载状态；修改内存不会自动持久化，由应用调用 `WriteStateAsync`。存储提供者可以通过 `Etag` 检测冲突，并在冲突时使写入失败。

借鉴到 Demo：

1. 同一玩家的命令由同一个 shard 的单个执行循环处理，减少余额检查与扣款之间的竞态。
2. 玩家状态单写者和持久化是两件事。不能因为“用了 actor”就把内存变动当作已持久化。
3. 后台写库应使用不可变快照或深拷贝，不能让数据库序列化时读取正在变化的背包 map。
4. 单机固定分片只提供本机的路由与排队，不拥有 Orleans 的分布式激活、目录和集群恢复能力。

不要把 Orleans 的默认行为理解成所有 grain 方法无条件禁止交错；原文明确存在 reentrancy 配置。本 Demo 选择更容易验证的非交错单写者模型。

## 2. Nakama：权威游戏循环和有界队列，存储层仍需事务及版本控制

来源：Heroic Labs 的 `heroiclabs/nakama`，固定提交 `81839b6ecaf08857c6d1f9c3fafb8a949718553e`。

- [server/match_handler.go](https://github.com/heroiclabs/nakama/blob/81839b6ecaf08857c6d1f9c3fafb8a949718553e/server/match_handler.go)：`NewMatchHandler` 建立带容量的 `inputCh`、`callCh`、`joinAttemptCh` 和 `signalCh`；一个 goroutine 的循环调用 match 函数；ticker 按 tick rate 驱动循环。`queueCall` 在队列满时停止 match，`QueueData` 在输入队列满时丢弃消息。
- [server/core_storage.go](https://github.com/heroiclabs/nakama/blob/81839b6ecaf08857c6d1f9c3fafb8a949718553e/server/core_storage.go)：`StorageWriteObjects` 在 `ExecuteInTxPgx` 内执行写入；`storageWriteObject` 的版本条件更新使用 `WHERE ... version = ...`，并返回版本冲突错误。

借鉴到 Demo：

1. 队列必须有上限。无限 goroutine 或无限 channel 只会把数据库/磁盘瓶颈转化为内存耗尽和长尾延迟。
2. 对资产 API，队满时应在接纳前显式拒绝，客户端带同一个请求 ID 重试；不能照搬实时位置消息“满了直接丢弃”的语义。
3. actor 解决本地执行顺序，版本检查与事务解决存储竞争；二者不能相互替代。
4. 定时游戏循环不等于定时持久化保证。match tick、客户端输入和资产持久性需要分别定义。

本 Demo 没有引入 Nakama，也没有实现其连接管理、会话、match 调度或 PostgreSQL 存储。这些源码是设计对照，不能作为本 Demo 的性能证明。

## 3. Redis：文件日志可以很严肃，落盘策略决定确认语义

来源：Redis 的 `redis/redis`，8.0 分支固定提交 `f49e5cb2b161418f92f2095c532b85ad24d80819`。

- [redis.conf：APPEND ONLY MODE](https://github.com/redis/redis/blob/f49e5cb2b161418f92f2095c532b85ad24d80819/redis.conf)：记录 `appendfsync always`、`everysec`、`no` 的差异；Redis 7 之后的 AOF 使用 base、incremental 和 manifest 文件组织恢复。
- [src/aof.c：flushAppendOnlyFile](https://github.com/redis/redis/blob/f49e5cb2b161418f92f2095c532b85ad24d80819/src/aof.c)：注释说明先把多次 AOF 写积累在内存缓冲，再在事件循环边界刷写；`AOF_FSYNC_ALWAYS` 路径执行同步操作，并在无法满足落盘承诺时退出；`EVERYSEC` 使用后台 fsync。

借鉴到 Demo：

1. 本地顺序日志不是“临时写个文本文件”。要处理校验、短写、落盘失败、尾部损坏、目录持久性、恢复版本及清理协议。
2. 多个请求共享一次 `fsync` 可以减少同步次数，但这些请求都必须等该次同步成功后才能得到持久化成功的确认。
3. “每秒后台同步”和“成功响应前落盘”是不同承诺。前者不能宣称进程、操作系统或机器故障下都零丢失。
4. 日志分段、快照和 manifest 是成熟系统的重要组成；只完成批量刷写并不等于具备完整 AOF 生命周期管理。

不要混淆 `write` 进入内核缓冲与 `fsync` 完成，也不要把 `fsync` 的软件契约提升为任何硬件故障下绝对不丢失的保证。实际持久性还取决于文件系统、存储设备、云盘与部署配置。

## 恢复协议比“每隔几秒保存”更重要

假设 MongoDB 快照保存的是玩家状态 `S200` 和 `last_seq=200`，WAL 有事件 201、202。启动恢复先加载 `S200`，再依次应用 201、202。必须满足：

1. 状态、幂等回执和日志进度来自同一份一致快照。
2. 事件可重放，不能在恢复时重新读取当前价格、抽奖随机数或外部时间来决定历史结果。
3. 后台开始写 `S200` 后，玩家若又生成 `S202`，写入 `S200` 成功只确认 200，不得清除 202 的脏标记。
4. MongoDB 返回结果不确定时，重复保存快照必须安全，旧快照不能覆盖新快照。
5. 只有已经被可靠快照覆盖的日志才可能回收；一个日志段中还有其他玩家的未落库事件时，不能按单个玩家的进度删除整段。

恢复过程中保留或拒绝损坏日志，应有明确规则和测试。故意跳过坏记录可能让金币和背包得到一个表面可读、实际错误的状态。

## 后续的生产化选择

如果真正的业务目标是跨节点高可用，优先评估成熟的状态与复制机制，而不是不断扩展自制本机日志：

- 数据库事务路径：更直接地协调资产、流水与幂等记录，代价是远端持久化进入请求延迟。
- 复制日志路径：由分区领导者或一致性组提供持久顺序，再由状态机执行；需要处理分区所有权、提交位置与重平衡。
- 本机 WAL + 定时快照：适合理解单写者、写合并和恢复；部署上必须明确持久卷、恢复时间与丢盘时的 RPO。

任何路径都要定义“什么时候算成功”和“哪些故障允许丢失多少数据”。HTTP 超时只代表客户端没有拿到确认，不能推导出操作未执行；幂等可以防重复应用，但不意味着网络获得了魔法般的 exactly-once 传输。

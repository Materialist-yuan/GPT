# 实际验证与测量记录

日期：2026-11-02。本文记录本次实际执行的检查，不将开源资料中的能力当作本项目的能力。

新增的相同Actor路径有/无WAL对照、CPU/内存profile和真实服务资源测量，见 [WAL成本基准](wal-benchmark.md)。下文原来的同步/Actor对照不能用于计算纯WAL开销。

## 功能、故障与构建

在 `wal-demo/` 中执行，全部命令成功：

```bash
source scripts/env.sh
bash scripts/mongo.sh
MONGO_TEST_URI=mongodb://127.0.0.1:27017 go test -race -count=1 ./...
go vet ./...
bash scripts/setup.sh
```

`setup.sh` 校验依赖并编译 `game-server`、`actor-server`、`loadgen`。真实 MongoDB 测试已启用，没有用跳过集成测试的普通单元测试结果代替。`TestActorProcessHelper` 在父测试中有意跳过，在 SIGKILL 测试启动的子进程中实际执行服务器。

已验证的重点：

- 原同步基线的幂等、并发重复发奖、余额不足及故障重放仍通过。
- WAL 批次只进行一次同步落盘；无效批次不写入，I/O 不确定时停止追加，完整前缀可恢复，完整记录损坏则拒绝。
- 后台快照被阻塞时，内存读写仍可执行；快照进行中的新变动不会被旧快照确认清除。
- 同一玩家重复请求只执行一次；成功与业务拒绝的状态码、结果都能从 WAL 重现。
- 队列、玩家、回执及未落库事件达到上限时显式拒绝；关闭与入队竞争不会挂起。
- Mongo 快照单调推进，旧快照不能覆盖新状态；不同日志身份、分片布局或丢失日志会拒绝启动。
- 数据库整体丢失、或已完成日志对应的玩家快照缺失时，拒绝静默启动。

### 真实进程强杀

`TestAcknowledgedAssetsSurviveSIGKILL` 启动真实 HTTP 服务子进程、使用独立 MongoDB 测试库和 WAL 目录：

1. 创建玩家、买剑、再买剑失败、奖励 50 金币，等待各 HTTP 响应。
2. 检查 MongoDB 玩家快照数量为零，确保没有靠快照绕过 WAL 恢复。
3. 对子进程发送 SIGKILL，原目录与数据库重新启动。
4. 检查余额为 70、剑为 1；重试四笔请求，分别返回原来的 201/200/409/200 和 `replayed=true`。

它验证的是保留本地盘的进程崩溃，不模拟断电、云盘丢失或跨机接管。

## 同机短负载对照

环境：Linux amd64，Go 1.27.3，MongoDB 8.0 固定摘要官方镜像；容器 CPU 配额为 4 核、内存上限 32 GiB（这是资源上限，不是测量到的使用量）。客户端、服务端、数据库共享宿主资源和本地存储。两个版本依次运行，使用独立数据库和 WAL；每轮 100 玩家、2,000 次奖励、32 并发 HTTP worker。

### 包含多轮快照的 Actor 负载

再对独立 Actor 实例执行：

```bash
./bin/loadgen -url http://127.0.0.1:8081 -players 100 -requests 50000 -concurrency 32
```

实际运行使用空闲本机端口和新数据库；URL 不影响负载模型。

- 奖励阶段 50,000 / 50,000 成功，耗时 10.665 s，成功吞吐约 4,688.2 次/秒。
- p50 / p95 / p99：5.30 / 15.59 / 29.22 ms；网络及协议错误为零，最终余额全部匹配。
- 最终 50,100 条事件合并为 8,274 个 WAL 批次；完成 44 次分片快照，快照错误为零。
- 等待最后快照完成后，四个分片 `pending` 均为零。100 ms 采样观察到总积压最高 8,854，这只是采样值，不能保证捕获真正峰值。

原始记录：[长负载](results/actor-long.json)、[最终统计](results/actor-long-stats.json)。这轮可能与其他开发验证共享 CPU，且只有约 11 秒；它用于证明快照链路实际执行并追平，仍不是长时间稳态性能或 SLO 认证。

Actor 的 HTTP 功能检查也已执行：`API_URL=... python3 scripts/smoke.py`，健康、目录、创建、购买、奖励、重复请求、失败回执及参数冲突均通过。

## 如何解读及继续实验

这些是单次、单机、闭环合成负载。请求 ID 与玩家集合每轮独立，样本包含失败尝试，错误会导致工具非零退出；没有在结果中删除失败样本。不能将本机请求/秒转换为在线玩家数量，也不能承诺生产环境相同延迟。

下一步应分别测量热点玩家、不同批量窗口、不同快照频率、数据库变慢、磁盘空间不足、持续数小时负载及跨机网络。需要特别观察：

- 微批等待时间与吞吐的交换，以及热点 shard 的队列长度。
- 快照和回执深拷贝造成的 CPU/GC 开销；当前不含冷玩家淘汰和高效持久化数据结构。
- 回执接近上限时的性能和拒绝行为；容量上限不是长期回执生命周期方案。
- 本页早期负载记录测量时尚未实现分段回收；当前 Actor 已支持 [回收协议](wal-reclamation.md)，需要继续测量大段扫描和回收期间的p99。
- 实际存储的 fsync 延迟和断电持久性；容器内文件系统测试无法证明物理硬件故障下的保证。

本次明确没有验证：跨节点复制、主从切换、分布式 fencing、在线迁移、跨玩家交易、充值对账、磁盘损毁恢复和生产身份权限。参考 [设计指南](actor-guide.md) 与 [开源调研](research.md) 继续扩展。


## 分段回收新增验证

当前版本再次执行 `MONGO_TEST_URI=mongodb://127.0.0.1:27017 go test -race -count=1 ./...`、`go vet ./...` 和 `bash scripts/setup.sh`，均通过。

- 分段测试：跨段全局序号、旧布局原子升级保留身份及降级保护、旧单文件接纳、混合玩家pending保护、安全前缀、覆盖证明、清单损坏/引用文件丢失拒绝、孤儿清理及未知文件保留。
- 5个真实子进程SIGKILL边界：清单rename前、rename后/目录同步前、清单目录同步后、unlink前和首次unlink后。恢复保留未完成事件、正确选择清单且不重用序号。
- 真实MongoDB：失败保存不回收，恢复保存后回收；回收后重启保留资产和幂等回执；被回收玩家快照丢失时拒绝启动。
- HTTP服务SIGKILL同时验证“尚无快照”和“已经实际删段，再确认尾部新奖励”两种状态，重启后资产与重复请求结果一致。

这些是软件崩溃测试，不是硬件断电或坏盘验证。早期性能数据保留原测量条件，不代表新回收逻辑无额外延迟。


### 实际文件回收观察

独立数据库与WAL目录，4分片、16KiB段软阈值、2秒快照周期：HTTP建100个玩家、发2,000次奖励，全部请求和余额检查成功。快照前保留日志998,403字节，追平后52,308字节，实际回收52个封存段，pending归零。

累计回收字节1,067,223大于前后体积差，是因为检查点确认时又追加了完成标记；这些字节也随旧段被删除。指标不包含清单、锁、文件系统元数据和设备写放大。原始记录见 [wal-reclamation.json](results/wal-reclamation.json)。此次真实Mongo检查使用原环境已有的8.0实例，没有据此宣称共享4.4服务已重新测过。

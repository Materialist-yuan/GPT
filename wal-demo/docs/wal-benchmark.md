# WAL 增加多少延迟：同路径基准与资源测量

2026-11-02 实测。此前的同步写 MongoDB / Actor 对比改变了整条持久化路径，不能据此计算 WAL 的成本。这次用相同 Actor 路径隔离日志成本，再另测真实 HTTP + MongoDB 服务资源。

## 测量方法

- Linux amd64、Go 1.27.3；CPU 配额 4 核，内存上限 32 GiB。
- WAL 文件在 `/workspace/GPT/wal-demo/data/benchmark-tmp`，文件系统为 overlayfs。**系统 `/tmp` 是 tmpfs，已排除其结果**；脚本显式设置 TMPDIR。
- 每模式 3 个独立进程，交替执行顺序；每轮 256 玩家、20,000 次奖励、32 个闭环 worker、4 个 shard，结束逐玩家核对余额。均成功。
- `no-wal` 只存在于测试二进制，跳过文件日志的编码、CRC、保留和 I/O。Actor 路由、业务状态、幂等回执、事件 JSON 生成和周期快照逻辑相同。生产入口没有关闭 WAL 的开关。
- 快照使用相同的内存存储适配器，**不含 HTTP、MongoDB、网络开销**，以隔离日志影响。批量64两组都有相同的1 ms收集窗口。
- 下表为三轮各指标的中位数，不是合并全部样本后的分位数；小样本没有统计显著性保证。编译不计入进程资源。

## 默认微批路径：WAL / 无 WAL

| 指标 | 无 WAL | WAL 落盘 |
| --- | ---: | ---: |
| 成功吞吐 | 22,288 次/秒 | 12,575 次/秒 |
| 单请求 p50 | 1.344 ms | 2.404 ms |
| 单请求 p95 | 2.327 ms | 4.031 ms |
| 单请求 p99 | 3.277 ms | 6.234 ms |
| 累计分配/操作 | 17,310 B | 20,942 B |
| 分配次数/操作 | 117 | 132 |
| 进程峰值 RSS | 40.3 MiB | 54.8 MiB |
| 进程 user + system CPU 时间 | 1.017 s | 1.572 s |

这组负载下，WAL 对照组的 p50 高约 **1.06 ms**、p99 高约 **2.96 ms**，吞吐低约 **44%**。这是包含排队、调度、日志处理和同步的整体差异，不是每次 fsync 的固定耗时，也不是生产 SSD 的通用结论。

批次上限虽然为64，实际平均约8条：32个闭环worker分散到4片，不能保证凑满。WAL 文件体积约519 B/操作，包含建号和可能发生的完成标记；它不是物理设备写放大或带宽测量。

CPU 时间及 RSS 来自 Linux `wait4`，覆盖进程的准备、预建玩家、负载、余额验证和关闭；延迟及 Go `B/op` 仅覆盖定时负载。CPU秒不是墙钟秒；`B/op` 是累计分配，不是驻留内存，也不能用RSS差值精确归因每一个对象。

## 逐笔同步与批量同步

去掉批量收集窗口、每次只处理一条命令时，同样进行三轮对照：

| 指标 | 无 WAL、batch1 | WAL、batch1 |
| --- | ---: | ---: |
| 成功吞吐 | 115,768 次/秒 | 6,112 次/秒 |
| p50 | 0.103 ms | 3.742 ms |
| p99 | 1.898 ms | 21.326 ms |

逐笔同步对磁盘和排队的影响明显。不要跨行用无WAL/batch1和WAL/batch64计算纯日志成本，因为两者的等待策略不同。无WAL时1ms收集窗口本身会限制吞吐；需要持久化时，微批能分摊同步成本。

另测仅追加约481 B的日志记录（不包含Actor），每组2,000次批次提交：

| 每批记录数 | 平均每批时间（含一次 fsync） | 摊销每条成本 |
| --- | ---: | ---: |
| 1 | 392 μs | 392 μs |
| 8 | 506 μs | 63.2 μs |
| 64 | 758 μs | 11.8 μs |

最后一列是批次成本除以记录数，不是单个玩家的确认延迟。该微基准只测 append，未包含检查点完成标记、并发竞争和恢复扫描。overlayfs 背后的虚拟化、设备和持久性不能由这些数字推断，应在目标持久卷重跑。

## 真正 HTTP + MongoDB 下的资源

另启动独立 Actor 服务，以100玩家、50,000次奖励、32 HTTP worker跑真实链路，默认每秒Mongo快照。请求与余额校验全部通过。此次资源测量使用原环境已有的 MongoDB 8.0 容器；推送时合并了远端改为共享 MongoDB 4.4 的基础设施调整，未将上述结果冒称为 4.4 的实测结果。纯 Actor / WAL 基准不连接数据库。

- 创建、奖励和余额检查合计约8.26秒。
- 服务进程 user CPU 13.52秒、system CPU 2.85秒，平均约 **1.98个CPU核**，即单核百分比口径约198%。
- 服务进程峰值RSS约 **191 MiB**，负载结束RSS约182 MiB。
- 资源统计**不含MongoDB进程、压测客户端和操作系统页缓存**。RSS峰值含启动，CPU差值不含启动及最终关闭。不能当作整个部署的资源预算或每玩家内存定额。

原始请求分位数、状态码、分片检查点统计与资源都在 [resource-load.json](results/resource-load.json)。这轮是约8秒的资源采样，不能代替小时级稳定性或内存泄漏检测。

## CPU / 内存热点

两种batch64模式另跑了CPU及分配profile，未混入上方无profile的延迟结果。原始二进制profile保留在本地忽略目录，文本摘要已提交。

WAL组的分配profile中，`cloneSnapshot` 累计约占66%的分配字节；这是快照及不断增长的幂等回执深拷贝的成本。WAL追加和JSON编码也占用CPU/内存，但不能把所有资源增长都归因磁盘。

这表明后续值得优化的是回执数据结构、批次内状态复制、检查点增量与回执生命周期；不应只为了跑分关闭fsync。profile包含准备和清理，采样比例也有波动。

## 复现

在 `wal-demo/` 下：

```bash
bash scripts/setup.sh
python3 scripts/benchmark.py data/benchmarks

# 真实HTTP/Mongo资源测量，使用独立随机数据库和WAL目录
bash scripts/mongo.sh
python3 scripts/resource_load.py data/resource-load.json
```

脚本保留原始输出，任何请求或余额验证失败都会非零退出。基准测试不要加 `-race`，也不要同时编译、跑其他负载。正确性验证单独运行 `MONGO_TEST_URI=... go test -race -count=1 ./...`。

本次没有做多小时soak、开放环流量、跨机网络、真实磁盘故障和不同云盘型号对比。下一步应在目标持久卷固定到达率压测，观察饱和点、队列、p99.9、GC、磁盘空间和检查点追赶速度。

# 单条、批量、等待窗口：完整实测矩阵

日期：2026-11-02。这里回答“批量是多个玩家，还是定时收集”：**当前实现两者都有，但提交触发条件是数量或时间先到，而不是定时才允许写。**

## 一批到底是什么

- 单条模式：一个事件一次追加，一次 fsync，成功后确认；不额外等待凑批。
- 批量模式：同一个分片中的事件共享一次 fsync。可以包含多个玩家，也可以包含同一个玩家的多笔操作，仍按队列顺序决定结果。
- 当前一个分片一个 WAL 文件。不同分片独立提交，没有所有玩家共用的全局10ms屏障。
- 第一条命令到来才启动收集窗口。收集到 `ACTOR_BATCH` 条命令，或 `ACTOR_BATCH_WINDOW` 到期，先满足哪个就提交；没有流量时不会为了凑批制造空业务事件。
- 批次包含命令，读取/幂等命中等不一定产生新日志，因此命令数量不等于新事件数量。
- 这不是跨玩家事务：进程崩溃时未确认批次可能只有部分完整记录留在日志中，恢复依靠日志校验和每笔请求的幂等协议。

例如同一分片收到 A玩家领奖、B玩家买剑、A玩家再领奖，这三笔可以共享落盘。每笔逻辑仍分别处理，批次里的成功响应都等 fsync 成功后才能返回。

```text
第一笔到来 → 开始收集 → 数量达到上限，或者窗口到期
                                      ↓
                              一组事件追加 + fsync
                                      ↓
                              发布状态，返回各笔结果
```

这与 MongoDB 每秒保存快照是两个独立过程。10ms是收集窗口，不是响应时间上限；排队、逻辑、调度和磁盘同步还会增加时间。定时器也不保证微秒级精确唤醒。

## 本次实际怎么测

三轮、19种场景，共57个独立测试进程，全部请求成功并核对最终余额。Linux amd64，4核CPU配额；WAL实际写到 `/workspace` overlayfs，排除系统 `/tmp` tmpfs。无WAL路径仅在测试二进制中存在。

- 均匀主负载：256玩家、32并发、每轮20,000次奖励，比较batch1、batch8、batch64，以及0/100μs/1ms/10ms窗口。
- 高并发补充：256玩家、256并发、每轮20,000次，观察接近满批的行为。
- 场景补充：单并发、单热点玩家、均匀短负载，每轮500次奖励。三个场景用同样的500次，避免直接拿不同样本数比较热点。
- 没有HTTP/Mongo网络开销：使用实际Actor状态机、日志、回执、事件编码，以及相同的内存检查点存储。未落库预算在基准中放宽，以隔离批量策略而非触发过载。
- 延迟和吞吐取三轮各指标中位数。资源为独立进程CPU秒及峰值RSS，包含准备、建号、验证和关闭；不是只测请求阶段。
- 500次短样本的p99波动较大，仅作行为对照。测试是闭环，不是固定到达率压测，不能推导集群容量。

## 高并发：批次能否接近64条

256玩家、256个闭环worker、每轮20,000次，单独三轮执行：

| 上限 / 窗口 | 实际事件/批 | 成功次/秒 | p50 ms | p95 ms | p99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 8 / 100μs | 7.93 | 25,639 | 8.265 | 23.855 | 32.594 |
| 64 / 1ms | 51.81 | 52,232 | 4.487 | 8.787 | 12.123 |
| 64 / 10ms | 63.29 | 53,364 | 4.116 | 8.918 | 11.157 |

10ms窗口在这里不一定等待10ms：若提前凑够64条，就立刻提交。这个场景与低并发下10ms拖延每笔响应并不矛盾。

注意：1ms组的个别轮次出现百毫秒级p99，原始结果保留，没有删掉长尾。当前短负载还受检查点捕获、GC、存储及调度时序影响；没有逐请求trace，不能把尖峰直接归因某一原因，也不能用这组峰值吞吐替代稳定SLO。需要更长、固定到达率测试进一步定位。

## 该怎么选择参数

1. 不要直接设10ms：低流量时可能每批只有一笔，却每笔都交了等待成本。32并发分散到4片时，也经常远达不到64条。
2. batch8与batch64在同一个100μs窗口下比较，才能较好地区分“数量上限”与“等待窗口”两个参数。
3. 收集窗口短可以降低低负载等待；逐笔同步则容易把磁盘次数和排队长尾放大。应结合真实持久卷、目标p99和流量形态调节。
4. 本次不能证明某个窗口永远最优，更不能因为一个场景的结果就自动修改生产默认值；本次保持默认1ms。
5. 后续需要补充固定到达率、热点混合比例、慢盘、不同持久卷、数据库积压与小时级soak。这里的“完整矩阵”指上述明确列出的19种场景，不代表所有部署和故障组合都已测过。

## 复现

在 `wal-demo/` 目录执行：

```bash
bash scripts/setup.sh
BENCH_MATRIX=1 python3 scripts/benchmark.py data/wal-matrix
```

每轮使用独立临时日志目录。脚本将TMPDIR指定到实际workspace文件系统，交替顺序运行三轮，保存延迟、吞吐、实际批量大小、CPU、RSS与分配量。不要同时运行其他压测或编译。任何操作失败或余额不符都会非零退出。

单独跑一个模式（先激活工具链并准备目录）：

```bash
source scripts/env.sh
mkdir -p data/benchmark-tmp
TMPDIR="$PWD/data/benchmark-tmp" BENCH_WORKERS=32 BENCH_PLAYERS=256 \
  go test -run '^$' -bench '^BenchmarkActorDurability$/^wal-batch64-100us$' \
  -benchtime=20000x -count=3 -cpu=4 -benchmem ./internal/actor
```

基准采用唯一请求ID并保留回执，不能无限增加同一玩家的操作次数来绕过容量限制。无WAL模式不具备相同持久性，只用于量化性能代价；服务入口没有提供关闭WAL的开关。
